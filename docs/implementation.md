# Реализация ADR-001 и состояние проверки

Исходный [ADR](adr.md) сохранён без изменений. Запрос на реализацию всего проекта расширяет указание в его конце про первую поставку Phase 0–2. Сначала реализованы клиент, decoder и CLI/domain, затем MCP. После добавления локальной cookie 2026-09-05 выполнена живая проверка: probe получил `200 text/x-script`, успешно декодировал ответ и нормализовал чеки; sync сохранил данные в локальную SQLite. Production fixture не фиксируется в репозитории, чтобы не переносить персональные данные.

## Что проверено

- Node 24, pnpm, strict TypeScript ESM; локальная SQLite через better-sqlite3.
- JSON envelope с `additionalReceiptsResponse` и runtime decode реального `text/x-script`/turbo-stream ответа X5.
- HTTP form из ADR, авторизация, редиректы, 429, сбои, отсутствие секретов в ошибках.
- Транзакции, замена items, идемпотентность, поиск по кириллице и буквальные SQL wildcards.
- Последовательная пагинация, границы месяцев, остановка повторяющихся страниц, сохранение частичного импорта, блокировка одновременных sync, отмена.
- Настоящий MCP stdio обмен через отдельный процесс, инструменты, prompts, валидация аргументов и аналитика SQLite.

## Внешний контракт

`tests/fixtures/history-page.json` — **искусственный пример на основе перечисленных в ADR полей**, не обезличенный production capture.

Decoder понимает JSON-объект с вложенным `additionalReceiptsResponse` и flattened stream v2. Используется [turbo-stream](https://github.com/jacob-ebey/turbo-stream), версия `2.4.1`. Массив в корне рассматривается как сериализация v2, не как готовый список чеков. Неизвестная форма не превращается в пустую историю. Поддержаны теги React Router `SingleFetchClassInstance`, `SingleFetchFallback`; ошибки и redirect останавливают импорт. Совместимость с реальным ответом X5 подтверждена 2026-09-05 на одном аккаунте.

Для нового аккаунта всё равно нужно локально добавить cookie, выбрать несколько дней с покупками и запустить `pnpm x5:probe --from ... --to ...`. После успешного probe синхронизировать небольшой период и сверить с сайтом даты, количество чеков, суммы, позиции с количеством >1, весовые товары, отсутствующую акционную цену и возвраты. Только после этого можно утверждать семантику цен для конкретной формы ответа. Не отправлять исходные headers или HAR в issue.

## Явные решения и отличия

- SDK `@modelcontextprotocol/server@2.0.0`, `serveStdio` с поддержкой старых клиентов. Подтверждено установленным пакетом и [официальной документацией MCP SDK](https://ts.sdk.modelcontextprotocol.io/v2/).
- Никакого OAuth и автоматического получения cookie. Он читается только из env/.env; редиректы не следуются, поэтому cookie не отправляется другой стороне.
- `amountPromo` → фактический итог чека, `amountRegular` → обычный итог. Отсутствующие значения → null, без выдумывания fallback.
- `pricePromo` сохранена как предполагаемая цена единицы, `priceRegular` — обычная цена. Отсутствующая акционная цена не заменяется обычной. `priceItem` хранится отдельно как `source_price_item_minor`, не используется для точных расходов. Значение `linePaid` внутри нормализатора — техническое имя этого исходного поля, а не доказанная семантика суммы строки.
- В живом ответе, проверенном 2026-09-05, код сети на уровне чека не пришёл в ожидаемом поле `codeTc`; сохранённые чеки получили `networkCode: null`. Фильтры по сети работают, когда поле есть в данных, но проект не пытается выводить сеть из адреса или названия магазина.
- Категорийная аналитика явно возвращает **оценки** на основе предполагаемой цены единицы. Округление выполняется по позиции. Не утверждает совпадение с суммой чека.
- Денежные входы преобразуются через десятичную строку и BigInt в безопасные целые копейки. Более двух знаков после запятой отклоняются до сохранения. Количество — вещественное, в том числе дробное; нулевое количество отклоняется. Возвраты не отбрасываются молча, однако реальные формы возвратов ещё не проверены.
- `rtlTxnId` — ключ; fallback SHA-256 от кода сети, фискального номера, номера чека и ISO времени. Если этих полей нет, чек отклоняется вместо рискованного объединения покупок.
- `created_at` хранится в UTC ISO, `purchase_date` — календарный день Europe/Moscow. Timestamp без offset трактуется как Москва. Для других часовых поясов РФ возможны пограничные случаи: при несовпадении с фильтром запрос останавливается, требуется сверка формата X5.
- Помимо таблиц ADR есть `sync_runs`, lease-блокировка между процессами, `purchase_date`, нормализованное имя для поиска. API не подтверждает полное покрытие истории сам по себе: статус complete означает завершённую пагинацию запрошенного диапазона.
- При сбое повторять тот же период: страницы сохраняются сразу, возобновление идёт с первой страницы с upsert, не с сохранённого курсора.
- `x5_get_product_history` требует PLU; неоднозначные названия сначала ищутся отдельным tool. Добавлены status, receipt detail, top products, категории и сравнение цен для пользовательских сценариев.
- Размер страницы HTTP ограничен 10 MiB, запрос — таймаутом; automatic retry при 429 отсутствует. MCP выдачи ограничены лимитами, недельные группы начинаются с понедельника.
- Probe не печатает даже первые 500 символов ответа: неизвестное тело может содержать персональные данные. Выводит безопасные числовые метаданные, а не исходный текст.
- SQLite не шифруется. Разные аккаунты должны иметь разные базы; cookie не используется как идентификатор аккаунта и не хешируется в базе.

## Пример нормализованного синтетического чека

```json
{
  "id": "synthetic-001",
  "createdAt": "2026-08-12T15:30:00.000Z",
  "purchaseDate": "2026-08-12",
  "networkCode": "D",
  "totalRegular": 26000,
  "totalPaid": 21998,
  "discount": 4002,
  "items": [{ "pluId": "coffee-001", "name": "Кофе Чёрный", "quantity": 2, "paidPrice": 10999 }]
}
```

Это иллюстрация нормализации, а не реальная покупка пользователя.
